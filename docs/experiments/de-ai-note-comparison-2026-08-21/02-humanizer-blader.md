# 当 ACUnit 开始自己决定开度和转速

ACUnit 是笔记本相变制冷系统的外机控制器。它由分电板、主控板和交互板组成，还要连接压缩机驱动、电子膨胀阀、风扇、压力与温度传感器、OLED、本地交互和网络接口。我在卷云实习期间独立完成了这三块 PCB 的设计、装配与焊接，随后编写固件，做分阶段 bring-up 和整机联调，也整理了 V2.1 开发 SOP。

第一阶段的固件已经能让 EEV 完成 Home、移动到目标脉冲，也能调风扇并向压缩机发送目标转速。我亲自验证过三块板的电气行为和各外设的独立工作，也把三块板、压缩机驱动板、压缩机、电源与电脑接在一起，跑通了完整链路。这些操作验证了执行链路，下一步的开度和转速仍由操作者判断。

后来的 `production-line` 分支保留手动测试入口，把自动决策放进一套可移植的板端控制核心。核心根据传感状态和运行模式计算 EEV 动作与压缩机转速。参考模型和回归资产放在控制逻辑周围，使算法可以暂时脱离 UART、OLED 和板级驱动单独推演。早期回归资产落后于最后的代码快照，所以旧结果不能充当最终版本的完整验证。

## 上电后先确认阀位和传感状态

每次上电，固件都进入 `AUTO + STOP`，不会恢复上次保存的非零风扇或压缩机输出。EEV 要先 Home，之后保存的开度才有明确的物理参照。启动时，阀先完成 Home 和预开，压缩机则等待传感状态有效，并遵守重启约束。严重条件可以越过启动宽限并接管控制。

普通温控只在状态可信时工作。传感无效可以阻止自动运行；低过热度或负过热度可以限制阀和压缩机；高冷凝压力可以降低允许的压缩机转速；压缩机调控温度持续过低时，系统可以停机。控制核心通过这些检查后，才执行普通温控目标。

## 200 ms 和 1 s 各有用途

压缩机控制路径每 200 ms 运行一次，依据出风调控温度和当前模式的转速上限连续调速。EEV 与安全路径每 1 s 决策一次。转速调节、阀动作和制冷状态变化的时间尺度不同，两个周期因此分开处理。

运行模式给这些决策设定边界。`STOP` 保持安全停机，`QUIET` 限制压缩机转速以照顾噪声，`PERF` 允许更高的制冷能力。`ZERO` 面向更低的出风温区，并有自己的低温停机行为。不同模式对应不同的输出边界，传感有效性与保护条件的优先级不变。

## 过热度怎么进入阀控制

固件用吸气温度减去吸气压力对应的蒸发饱和温度，得到过热度：`SH = Ts - Tevap_sat(Ps)`。压力和温度由此进入同一个判断。当前代码使用 R134a 近似压力温度表；冷媒改变或传感器量程调整后，表格也要替换并重新验证。

[Danfoss 的电子膨胀阀控制资料](https://www.danfoss.com/en-us/service-and-support/case-stories/dcs/the-pioneer-in-electronic-expansion-valve-control/)说明了这里涉及的通用制冷原理：过热度太低会增加湿回流和压缩机风险，最低稳定区域还会随负载与吸气压力变化。这能解释固定开度为何无法覆盖所有工况。资料并未验证 ACUnit 的具体阈值。

`production-line` 分支的代码加入了低开度阻尼，也把趋势与预测约束、低过热度和负过热度处理、压缩机协同限制纳入控制。从仓库里能确认的是，这些处理已经写进实现。参数是否完成标定，仍要看后续实机证据。

## 后期实机反馈的边界

公司测试团队后来反馈，`QUIET`、`PERF` 和 `ZERO` 都在真实制冷系统上运行过。他们观察到 EEV 过热度控制和压缩机连续调速带来的变化。团队还报告，低过热度、负过热度与高冷凝压力保护曾在实机触发。

我没有亲自执行或旁观这些后期测试，也没有取得足以逐次核对事件的原始日志。因此，这部分结果只能按公司测试团队的反馈记录，不能改写成我的实测结论。

现有代码和反馈支持自动控制已经能够运行。模式目标、阈值、最低开度和响应时间还需要在真实冷媒回路、负载及环境条件下长期标定，目前的材料不支持 `量产参数已经完成` 这一结论。
