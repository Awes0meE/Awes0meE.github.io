# “能跑”改了三次意思：Seamly2D 三周开发记录

> 原公开摘要：三周全职实习把“能跑”拆成越来越具体的检查：先让分支、Qt 与编译器对齐，再让本地账户规则进入界面，最后验证 Release、Windows 安装包与 macOS 无签名 DMG。

## 进度条走了 10%，我先学会了镜像是什么

八月第一周刚在南京打完 2025 年全国大学生电子设计竞赛，第二周我就坐进研究院办公室，开始连续三周的全职实习。每天早上八点到、下午五点走，带教工程师给出当天任务，我做完再去汇报。节奏很正式，起点却很初学者。我知道一点 C/C++ 语法，从没用过 Qt，也没进过这种体量的开源项目。

第一天的任务是把开发环境装起来。Git、MSVC v142、Windows SDK、CDB、Qt Creator 和 Qt Kit 一项项排开，看上去像安装清单；真正耗时间的是 Qt 在线安装器。海外服务器下载三个小时，进度大约 10%。我没有意识到这件事还有别的解法，只觉得「大软件可能就是要下这么久」，于是非常老实地陪了它一天。带教工程师第二天问清情况，告诉我可以换清华镜像。切过去以后，一个多小时就结束了。

这件事现在想起来仍然很好笑。我从电赛现场出来，自以为马上要学复杂的桌面 UI，结果第一份有效经验是下载源也属于开发环境。清华 TUNA 现在的 [Qt 镜像说明](https://mirrors.tuna.tsinghua.edu.cn/help/qt/)直接给出了在线安装器的 `--mirror` 用法；当时的我晚一天才知道，刚好交了一点新人学费。

## qmake 通过了，源码还站在 Qt 6 那边

环境装好后，我第一次 clone Seamly2D，查看上游分支，再把代码拉到公司为实习生准备的开发线上。最初选择 Qt 5.15.2，是因为那套安装与 Kit 看起来已经齐全。工程里的 `core5compat` 先让 qmake 报错；我把它改成条件加载，清理后再次执行，终于看见 `qmake_all finished successfully`。

然后完整构建冒出三十多个错误。

`QStringConverter`、Qt6 侧头文件和调用方式已经散在当前源码里。qmake 能生成构建文件，只证明 `.pro` 文件已经被处理，并没有替编译器承诺「这条分支兼容 Qt 5」。如果坚持原路线，就要给一批代码补 Qt 5 条件编译。对一个刚认识 Qt 的三周实习生来说，这条路既慢，也偏离任务。

我改装 Qt 6.5.3 MSVC2019 64-bit 与 Qt 5 Compatibility Module，选择 v142 编译器，删除旧 build 目录和 `Seamly2D.pro.user`，重新配 Kit。再次 qmake、完整构建，源码与工具链才终于站到同一边。[Qt6 首跑原始记录](/notes/turing-qt-seamly2d-first-run)保留了这些修改，也保留了我当时那种「每解决一个错误，才发现前一个成功只负责一小段」的推进方式。

现在查 Qt 6.5 的[支持配置](https://doc.qt.io/qt-6.5/windows.html)，Windows、x86-64 与 MSVC 2019 本来就被并列写在同一组条件里。那次排查让我第一次意识到，版本号、编译器和架构不是安装界面里三条互不相干的信息，它们共同决定一个二进制世界能不能接上另一个。

## 回车键连着取消，权限还没来得及复杂

第一周后半段，我开始在 Seamly2D 主界面前增加本地注册与登录。最初版本用 `QSettings` 保存用户信息，密码也只是明文存储和字符串比较；随后我把它改成哈希值存储与校验，并将密码框设为遮蔽显示。用户已经存在、用户不存在、密码错误，各自需要明确提示。到这里看起来仍然像一项普通的窗口开发任务。

窗口很快证明自己没有那么普通。登录和注册界面的回车键默认连到了取消，用户名输入会弹联想，密码框在中文输入法状态下还发生过闪退。它们都不是「核心功能」，却会在用户真正操作时抢先出现。尤其是中文输入法崩溃，问题完全没有长成权限逻辑的样子，却能让整个入口当场消失。

我逐项修正输入行为，再在 `main()` 附近整理注册、登录和进入主程序的顺序。`QSettings` 负责的是本机持久化，不是远程用户系统；Qt 官方也把 [`QSettings`](https://doc.qt.io/qt-6.5/qsettings.html)描述为跨平台应用设置抽象。数据库与在线鉴权会是另一套架构，不在这次实习范围内。这三周只验证现有 C++ 桌面程序能不能先多一层可靠的本地入口。

## 管理员不是一个菜单，而是一组不允许发生的转换

第二周，账户从「能不能登录」继续长到「登录以后能做什么」。首次注册的用户名必须是 `admin`；角色分为普通用户和管理员；只有管理员看得到用户管理。删除操作要二次确认，而且管理员只能删除普通用户。升级同样只对普通用户开放，降级则只能由 `admin` 执行，避免其他管理员互相改回普通用户。

这些需求写在周日志里很像一列功能，查看、删除、升级、降级。真正实现时，每一项都在问当前用户、目标用户、目标角色和允许的下一状态。到了这里，我对 GUI 的理解才从页面上有哪些控件稍微转了一下。界面只是状态露出来的地方，真正需要守住的是哪些转换根本不该发生。

[公开角色摘录](/uploads/projects/nanjing-turing/auth-role-snippet.cpp)只保留本地 `Role::User`、`Role::Admin` 与角色查询，没有重发完整账户源码。[第二周原始日志](/uploads/projects/nanjing-turing/week-2-development-log.txt)则按当时顺序留下了整组限制条件。

## `windeployqt` 明明在电脑里，构建就是看不见

第三周的目标从 Develop 转向 Release。此前我已经能在 Qt Creator 里启动带账户入口的程序，于是很自然地觉得接下来就是把它导出来。`windeployqt` 很快把这个理解卡了三天。部署步骤说找不到命令，可执行文件却明明躺在 Qt 安装目录里。重装、查路径、重新配置，我已经记不清所有尝试的顺序，只记得这三天确实很烦。

好在当时的文档留下了最终方案。Qt Creator 的 Build Environment 需要看到 Qt `bin`；两个 `.pro` 文件里的 post-link 规则也改成通过 `QT_INSTALL_BINS` 定位 `windeployqt`，并限制在 Release 配置下执行。环境变量不只是系统设置窗口里的一长串路径，它还要真的进入启动构建任务的那个进程。工具存在于硬盘，并不等于当前构建环境有能力找到它。

Qt 6.5 的 [Windows 部署说明](https://doc.qt.io/qt-6.5/windows-deployment.html)把 `windeployqt` 的工作描述为扫描 `.exe`，收集 Qt 库、插件、翻译和运行时文件。它还特意提醒第三方库不在自动处理范围内。于是部署目录铺满 DLL 后，程序仍然缺 `xerces-c_3_2.dll`，就不再是一件反常的事。Seamly2D 用 XML 保存纸样数据，Xerces-C++ 是它另外依赖的 XML 库，当然还要手动补进来。

这时第三周前面读过的 `.sm2d` 与 `.smis` XML 样例又回到了眼前。文件里的纸样点、线、曲线和量体变量，最后都要穿过实际解析库才能被程序读取。[XML 样例笔记](/notes/turing-sm2d-xml-data-format)保留数据结构，[CMake 与编译逻辑笔记](/notes/turing-cmake-build-logic)则是我为了分清编译器、链接器、生成器、Ninja、Qt 包发现和运行时依赖而补的另一条学习线。Seamly2D 本身始终使用 qmake；我没有把它迁移到 CMake。

## 安装包在开发机启动，不等于故事已经结束

依赖补齐后，我继续创建 Windows 自签名证书，用 Inno Setup 把零散文件做成安装程序，再给程序和安装包签名。编译、依赖收集、签名、打包、安装、启动，这条链在实习电脑上完整跑过；带教工程师也在最终验收里逐项看了账户功能和 Windows 部署结果。

当时的[打包流程文档](/notes/turing-release-packaging-cross-platform)在结尾写得很诚实。手头没有一台既无 Visual Studio、也无 Qt 的 Windows 设备，所以正式实习记录只证明开发机本地安装成功。README 里那句「移植到任意电脑都可以运行」写得比当时证据快了一步。

实习结束约半个月后，我回到家，在一台新装的 Windows 台式机上补了这次验证。那台机器没有 Qt，也没有 Visual Studio；我运行 Inno Setup 生成的安装程序，安装后实际打开了带注册、登录和权限功能的版本。这次测试发生在旧文档完成以后，没有补回文档，也没有再找导师复验。它不是公司正式验收的一部分，但确实把换机运行从一句预期变成了我亲自做过的结果。

## 换成自己的 Mac，源码没有顺便带来信任身份

Windows 完成以后，我把同一份代码搬到自己的 Mac。Homebrew Qt 与官方 Qt 的路径和架构不同，原来的 Windows Kit 更不会跟着源码一起过来。我重新跑通 Debug、Release，用 `macdeployqt` 收集 Qt framework 和插件，应用实际启动，无签名 DMG 也生成并在这台 Mac 上打开过。带教工程师现场看了演示。

签名停在下一步。我创建了自签名证书，又写了一份包含 `codesign`、`spctl` 和 DMG 生成顺序的脚本，但应用签名始终没有完成，更没有进入 notarization。Qt 的 [`macdeployqt` 文档](https://doc.qt.io/qt-6.5/macos-deployment.html)解决的是应用包里的 framework 与插件；Apple 的 [Developer ID 说明](https://developer.apple.com/support/developer-id/)处理的是另一件事，也就是系统怎样确认分发者身份，以及软件是否经过 Apple 的公证检查。

所以 DMG 已经生成与这个应用可以正式分发之间并不只差一个压缩命令。第一份脚本保住了[实际跑通的无签名路线](/uploads/projects/nanjing-turing/macos-build-package.sh)，第二份脚本保住了[没有完成的签名尝试](/uploads/projects/nanjing-turing/macos-build-package-sign.sh)。脚本能记住顺序，不能替我申请 Developer ID，也不能自动把一次失败写成成功。

## 三周最后提交进 `develop`，绿色三角留在了起点

这也是我第一次把 Git 从下载 GitHub 代码用成协作工具。clone、查看和切换上游分支、建立自己的开发分支、commit、push、merge、pull request、fork 和 tag，我都在实战里走过。公司专门为实习生设置了 `develop` 分支；最终源码、修改、日志和交接材料提交到这条分支。离开以后公司是否继续采用或产品化，我不知道，也不会替后续补结论。

正式验收时，带教工程师从注册登录、角色管理一路检查到 Windows 安装与 Mac 演示。他最后特意说，从三周前完全不知道 Qt，到现在能把一个大型项目推进到这个程度，进步很大。他确实夸了我很久，我也确实兴奋。那不是因为我突然成了 Qt 专家，而是我第一次确认，面对一套陌生的大型代码，我可以沿着错误、分支和依赖慢慢进去，最后把自己的改动交出去。

在这之前，「能跑」差不多就是命令行程序给出正确输出。三周以后，它必须带上条件。哪个分支、哪套 Qt、哪个角色、哪种构建、哪台机器、有没有平台信任。Qt Creator 的绿色三角没有失效，只是从终点退回了它本来应该待的位置，也就是一条更长验证链的起点。
