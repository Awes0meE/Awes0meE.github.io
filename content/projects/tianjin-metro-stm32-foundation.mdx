## The Magic Wand Had to Work Before GPIOC13 Could Blink / 魔术棒配置完，GPIOC13 才有机会闪

In February 2025, I joined Tianjin Jintie Communications Co., Ltd. for a one-month placement under the formal title of Embedded Systems Intern. My internship certificate came from Jintie Communications, while my desk was inside the Tianjin Rail Transit Group headquarters. [The Group's public disclosure](https://static.cninfo.com.cn/finalpage/2024-04-30/1219962825.pdf) identifies it as fully owned within the Group structure. The setting sounded close to railway engineering, but the first objects on my desk were much smaller. They were an STM32F103C8T6 Blue Pill, an ST-Link, and a collection of introductory material from the supervising engineer. This was a training exercise, not work on a production rail system.

The material did not arrive with a daily syllabus, which was fair for a one-month intern. I combined it with online tutorials and arranged my own sequence. GPIO led to EXTI, then Timer, PWM / UART / ADC, and finally an integrated demo. Before this, I had only used an Arduino Nano in university projects. My entire mental model of a microcontroller was little more than calling one function for high and another for low.

The first real obstacle was not C code but Keil's Magic Wand settings. Device support packs, compiler selection, library paths, target addresses, and ST-Link download options appeared together before I understood what a startup address or flash algorithm was responsible for. Build Succeeded only meant that the computer had produced a program; it did not mean the program had reached the board. A 300 ms blink on GPIOC13 became my first end-to-end test, crossing the project, compiler, programmer, MCU, and physical pin.

The smallest code excerpt enables the GPIOB and GPIOC clocks, establishes the OLED module's power levels on PB4 and PB5, and then alternates PC13. It was the first time I noticed how much an Arduino API had kept out of sight. A peripheral clock must exist before the port can work, and the pin's mode, speed, and initial level still have to be chosen. ST's [Standard Peripheral Library](https://www.st.com/resource/en/application_note/an3268-stm32vldiscovery-firmware-package-stmicroelectronics.pdf) shortened the register syntax; it did not make those hardware decisions for me.

2025 年 2 月，我以「嵌入式实习生」的岗位进入天津津铁通信有限公司实习。实习证明由津铁通信出具，日常办公地点却在天津轨道交通集团总部；[集团公开披露材料](https://static.cninfo.com.cn/finalpage/2024-04-30/1219962825.pdf)把这家公司列为其体系内全资持股的企业。听起来像是离轨道工程很近，落到我桌上的东西却很朴素，只有一块 STM32F103C8T6 Blue Pill、一只 ST-Link，以及工程师发来的一批入门资料。这是培训练习，不是生产轨道系统开发。

工程师没有顺便附上一张逐日课程表。对一个只实习一个月的新人来说，这也很合理。我根据资料、网上教程和自己的理解，把路线排成 GPIO → EXTI → Timer → PWM / UART / ADC → 综合 demo。此前我只在学校项目里用过 Arduino Nano；对单片机的全部理解，差不多就是调用一个函数把端口拉高，再调用另一个函数把它拉低。

真正拦住我的第一关甚至不是 C 代码，而是 Keil 那个「魔术棒」设置页。器件支持包、编译器、库路径、目标地址和 ST-Link 下载配置同时出现时，我连启动地址和下载算法各自负责什么都说不清。工程显示 Build Succeeded，只能证明电脑生成了程序，不能证明程序已经进到板上。于是 GPIOC13 的 300 ms 闪烁成了第一个端到端检查。从工程、编译、下载，一直走到真实引脚，链路中任何一段没接上，它都不会按预期变化。

公开摘录先使能 GPIOB、GPIOC 时钟。GPIOB 的 4、5 号引脚给 OLED 建立供电电平，GPIOC13 再以 300 ms 为间隔翻转。那时我第一次注意到，`GPIO_SetBits()` 之前还有一串不会被 Arduino API 主动讲给我的选择。外设总线时钟要先打开，引脚模式、速度和初始电平也要明确。ST 的[标准外设库](https://www.st.com/resource/en/application_note/an3268-stm32vldiscovery-firmware-package-stmicroelectronics.pdf)缩短了寄存器写法，却没有替我做掉这些硬件决定。

## Below SetBits Were Clocks, Modes, and Registers / 一行 SetBits 往下，还有时钟、模式和寄存器

While learning GPIO, I deliberately followed the library calls downward. On the F103, GPIO, AFIO, ADC, and some USART clocks are enabled on APB2, while TIM2–4, I²C, and other USART peripherals sit on APB1. A pin must then be configured as an input, push-pull output, open-drain output, or alternate function. The [RM0008 reference manual](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-arm-based-32-bit-mcus-stmicroelectronics.pdf) let me connect the library routines to the RCC and GPIO configuration registers. `SetBits` stopped looking like an incantation; it was simply the last visible action in a longer hardware path.

EXTI and timers split the next question in two. Which edge just occurred, and when should this happen again? The encoder turned pin transitions into events. Timers derived update rhythms from their clocks, prescalers, and counter periods. In the integrated project, `Encoder_EXTI_Config()`, `TIM3_Config()`, and `TIM4_PWM_Config()` appeared together, but they dealt with edge capture, task pacing, and a PWM time base, not three differently named delays.

我学习 GPIO 时有意往函数下面追。以 F103 为例，GPIO、AFIO、ADC 和部分 USART 的时钟开关位于 APB2 侧，TIM2–4、I²C 和另外一些 USART 则在 APB1 侧；引脚随后还要在输入、推挽输出、开漏输出或复用功能等模式间选择。[RM0008 参考手册](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-arm-based-32-bit-mcus-stmicroelectronics.pdf)让我看见了库函数与 RCC、GPIO 配置寄存器之间的对应关系。`SetBits` 不再像一句咒语，它只是整条硬件路径最后露在代码表面的那个动作。

接着学 EXTI 和 Timer，问题又从「现在是高还是低」分成了「哪一个边沿发生了」和「多久以后再发生一次」。编码器需要把引脚变化变成事件；定时器则把时钟经预分频和计数周期变成更新节奏。后面的综合工程里，`Encoder_EXTI_Config()`、`TIM3_Config()` 与 `TIM4_PWM_Config()` 会同时出现，但它们分别处理边沿、任务节奏和 PWM 时基，并不是三个名字不同的 delay。

The OLED gave me a more concrete lesson. The code compiled and flashed, the wiring looked correct, yet the display stayed blank. Moving the bus to another pair of ordinary GPIO pins and bit-banging I²C brought it back. During the internship, all I knew was that changing pins worked. In hindsight, ST's [F103x8/xB errata](https://www.st.com/resource/en/errata_sheet/es096-stm32f101x8b-stm32f102x8b-and-stm32f103x8b-mediumdensity-device-limitations-stmicroelectronics.pdf) documents a hardware-I²C condition that can leave the BUSY flag locked, so the explanation is technically plausible. I did not retain the BUSY register state, waveforms, or exact pins, however, so it remains a present-day hypothesis rather than a proven root cause. The observed failure, the switch to software I²C, and the recovered display are the parts I can state with confidence.

OLED 还给了我一次更具体的教训。代码能编译、能烧录，接线看起来也对，屏幕却始终不显示。最后我换到另一组普通 GPIO，用软件模拟 I²C 后才恢复。实习当时我只知道「换引脚能用」；现今回看，ST 的 F103x8/xB [芯片勘误](https://www.st.com/resource/en/errata_sheet/es096-stm32f101x8b-stm32f102x8b-and-stm32f103x8b-mediumdensity-device-limitations-stmicroelectronics.pdf)确实记录过硬件 I²C 的 BUSY 锁死情形，因此它是一个技术上说得通的解释。但当时没有保存 BUSY 位、波形或确切引脚记录，我不能把它写成已经定位的根因。真正确定的只有故障现象、换成软件 I²C 的动作和屏幕恢复的结果。

## Sixteen Points Carried an ADC Target into TIM4 / 16 个点，把 ADC 数字送到 TIM4

PWM, UART, and ADC taught me to separate data by purpose. ADC turned the light sensor's analogue voltage into a sample. PWM used a timer period and compare value to shape the pulses seen by an LED or servo. UART carried light readings and debug text to a computer. All three moved numbers, but they served measurement, actuation, and observability rather than forming one interchangeable kind of interface.

To map a target light reading to an LED output, I changed the PWM setting point by point and recorded the resulting ADC values. The 16 measured pairs run from PWM 0 / ADC 1600 to PWM 1000 / ADC 480. `Lookup_PWM_For_Target()` locates the two points surrounding a target, linearly interpolates between them, and writes the result to TIM4 channel 1. The divider orientation made the ADC value fall as the PWM value rose. I did not convert the readings to lux or characterize fitting error; the calibration answered which compare value worked for this breadboard setup, not its photometric accuracy.

学 PWM、UART 和 ADC 时，我开始把「数据」按用途分开。ADC 把光敏传感器的模拟量变成采样数字；PWM 用定时器的周期与比较值决定 LED 或舵机收到的脉冲；UART 则把光照数据和调试文字送到电脑。它们都在传数，却分别承担采样、执行和观察，不能因为最后都落进变量就混成一类接口。

为了让目标光照数值能对应到 LED 输出，我没有凭感觉写一条直线，而是逐点改变 PWM、读取 ADC，记下 16 组数据。表格里 PWM 从 0 增到 1000，ADC 从 1600 降到 480；目标落在两点之间时，`Lookup_PWM_For_Target()` 做线性插值，再把结果写进 TIM4 通道 1。传感器分压方向使数值呈反向变化，但这里没有换算照度单位，也没有测量拟合误差。标定解决的是这套面包板接法下该写多少比较值，不是计量级光照测量。

This path is easy to mislabel as closed loop, but the code is more precise. The target is mapped directly to PWM, while measured light is read, displayed, and printed over UART. There is no target-minus-measurement error and no correction based on that error. It is a feedforward calibration with visible measurement. I remember considering feedback at the time; it did not make it into the final code.

这条路径最容易被说成闭环，代码却给出了更诚实的答案。目标值直接查表得到 PWM，实测光照只被读取、显示和通过 UART 打印，没有形成目标减实测的误差，也没有据此继续修正输出。它是一条带实测可观察性的前馈标定路径。我当时确实想过继续做反馈，但没有把那个想法写进最终代码。

## Every Peripheral Finally Had to Share One main() / 所有外设终于挤进同一个 main()

GPIO, OLED, encoder, servo, DHT11, light sensing, PWM, and UART first ran as separate exercises. I then joined them in one bare-metal program around the same Blue Pill, breadboard, and Dupont wires. There was no custom carrier board. A button switched what the encoder controlled. One mode changed target light, while the other changed servo speed. GPIOC13 acted as a status indicator. The OLED showed measured light, target, LED output, temperature, and humidity, while UART sent light data and debug messages to the computer. All of these functions ran together in the final bench demo.

The condensed main-loop excerpt preserves the light-control path. `Get_Encoder_Value()` changes the target; a flag gates light-sensor and DHT11 reads; the OLED exposes the values; and the lookup result drives the LED PWM. The complete internship project also contained the button-mode, servo, and UART branches, which this shorter file does not reproduce. I wrote the application flow, encoder mappings, calibration interpolation, mode switching, and integrated superloop. I adapted the OLED, DHT11, encoder, and other drivers from ST library material and public examples rather than inventing those drivers from a blank file.

There was no RTOS. Interrupts and timer flags handled some events and polling rhythms; the superloop carried the remaining work; several delays were still blocking. That was usable for a low-frequency demo built around temperature, humidity, a rotary input, and lighting. With tighter real-time work, the blocking delays, shared state, and execution time of each branch would all need to be redesigned.

前面的 GPIO、OLED、编码器、舵机、DHT11、光敏传感器、PWM 和 UART 都先以独立工程跑通，最后才被接进同一个裸机程序。Blue Pill 周围是面包板和杜邦线，没有定制扩展板。按键切换编码器的控制对象。一种模式改变目标光照，另一种模式改变舵机速度；GPIOC13 留作状态指示；OLED 同时显示实测光照、目标、LED 输出和温湿度；UART 把光照数据与调试信息发到电脑。所有外设在最终 demo 中能够同时工作。

公开的主循环摘录保留了光照这条主线。`Get_Encoder_Value()` 改变目标，flag 到来后读取光敏传感器与 DHT11，OLED 刷新数值，查表结果交给 LED PWM。完整实习工程里还有按键模式、舵机和 UART，当前公开摘录没有把这些分支全部展开。应用层流程、编码器数值映射、标定插值、模式切换和综合主循环由我编写；OLED、DHT11、编码器等驱动则是在 ST 标准库和公开例程基础上理解、修改和接入，不把它们说成从零独立发明。

这个程序没有 RTOS。中断和定时器 flag 负责一部分事件与轮询节奏，主循环串起其余工作，某些延时仍是阻塞式 `delay`。对于温湿度、旋钮和灯光这种低频 demo，它确实能跑；但再加入更严格的实时任务，阻塞延时、共享状态和各分支执行时间都会变成需要重新设计的问题。

I completed this sequence independently in roughly 20 working days. At the end, the supervising engineer watched the demo and listened to my explanation of the peripherals, then said I had learned the material solidly. It was an informal review, not a formal acceptance. The engineer's training material also introduced PID, ATP, ATO, and ATS. I studied the concepts, but I did not implement or tune PID and never worked on a real train-control system. China's [operational technical specification for urban rail signal systems](https://xxgk.mot.gov.cn/jigou/ysfws/202201/P020220121613617393399.pdf) places ATP protection, ATO train operation, and ATS supervision within reliability, redundancy, and verification requirements far beyond this Blue Pill demo. The useful resemblance was smaller. Inputs, state, timing, communication, and outputs met inside a controller.

The part that carried furthest into my later work was the path to field-oriented motor control. In FOC, a timer is no longer just a periodic trigger, ADC is no longer just a light-sensor read, and PWM is no longer just a way to dim an LED. Sampling must be aligned with PWM, and the control calculation must finish before the next update. ST's [motor-control documentation](https://www.st.com/resource/en/user_manual/um1052-stm32f-pmsm-singledual-foc-sdk-v43-stmicroelectronics.pdf) puts those resources on one synchronized chain. The Tianjin internship did not turn me into a motor-control engineer, but when I later encountered that chain, I did not have to begin again with the question of why a microcontroller was more than a collection of convenient functions.

这约 20 个工作日的路线由我独立完成，工程师最后看过 demo，也听我讲了对外设的理解，评价是「学得比较扎实」。这是一次非正式检查，不是项目验收。工程师给的材料还引出了 PID、ATP、ATO 和 ATS；我认真读了原理，却没有实现或整定 PID，更没有接触真实列车控制。[交通运输部的城市轨道交通信号系统规范](https://xxgk.mot.gov.cn/jigou/ysfws/202201/P020220121613617393399.pdf)把 ATP 的安全防护、ATO 的列车自动运行和 ATS 的监督协调放在远比这块 Blue Pill 更严格的可靠性、冗余与验证约束下。我的 demo 能提供的只是一个缩影。输入、状态、时序、通信和输出如何在控制器里相遇。

这段实习真正延续到后面的地方，是 FOC。到了电机控制项目里，Timer 不再只是周期触发，ADC 不再只是读一个光敏值，PWM 也不再只是调灯；采样时刻要和 PWM 对齐，控制计算要赶在下一次更新前完成。ST 的[电机控制文档](https://www.st.com/resource/en/user_manual/um1052-stm32f-pmsm-singledual-foc-sdk-v43-stmicroelectronics.pdf)把这些资源放在同一条同步链路上。天津实习没有把我直接变成电机控制工程师，却让我在后来第一次看到这条链时，不需要再从「单片机为什么不只是几个函数」重新开始。
