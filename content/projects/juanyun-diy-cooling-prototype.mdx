## Nine Build Plates Before Any Airflow Claim / 九块切片板还不是风量证据

Three Bambu Studio screenshots show the same group of orange enclosure and duct parts from different preparation views. One highlights automatic tree supports, another the brim and skirt settings, and the third manual tree supports and several part orientations. The linked 3MF carries nine build plates and names such as `上盖右.STL`, `下盖左.STL`, and `右上type-c接口.STL`. Together they record how split shell parts were arranged for an A1 mini-class build volume.

三张 Bambu Studio 截图其实盯着同一组橙色壳体与风道零件，只是准备视角不同：一张圈出树状自动支撑，一张停在 Brim 与 Skirt 参数，另一张换成树状手动支撑并标出几种摆放姿态。相邻的 3MF 里有九块切片板，还能读到 `上盖右.STL`、`下盖左.STL`、`右上type-c接口.STL` 这些分件名。它们合在一起，能说明拆分后的壳体怎样塞进 A1 mini 一类的成形空间。

![Automatic tree-support view for the same part set / 同一组零件的树状自动支撑视图](/uploads/projects/juanyun-tech/diy-cooling-3d-print-preview-1.jpg)
![Brim and skirt settings for the same part set / 同一组零件的 Brim 与 Skirt 设置](/uploads/projects/juanyun-tech/diy-cooling-3d-print-preview-2.jpg)
![Manual tree-support view and part orientations / 树状手动支撑与零件摆放视图](/uploads/projects/juanyun-public/diy-cooling-3d-print-preview-3.jpg)

These are slicing and support records, not three proven mechanical revisions. They also contain no printed-dimension check, pressure or flow measurement, or comparison between duct geometries. The [A1 mini 3MF](/uploads/projects/juanyun-public/diy-cooling/bambu-a1-mini-auto-slice.3mf) preserves print preparation; it cannot show whether the assembled duct moved air as intended.

所以，这三张图更适合叫“切片与支撑设置比较”，还不能叫三个已经验证过的机械版本。材料里也没有打印尺寸检查、风压 / 风量测量，或不同风道几何之间的对照。[A1 mini 3MF](/uploads/projects/juanyun-public/diy-cooling/bambu-a1-mini-auto-slice.3mf)保住了打印准备过程，却回答不了装起来以后风是不是按设想流动。

## Two Text Prefixes Join Windows and ESP32 / 两个文字前缀把 Windows 与 ESP32 接起来

The desktop endpoint is small enough to follow in one source file. [Form1.cs](/uploads/projects/juanyun-public/diy-cooling/desktop-form1.cs) asks LibreHardwareMonitor for CPU and GPU temperature sensors. Every 5000 ms, a WinForms timer schedules one monitor task and an independent send task. The sender alternates between `CPU{value}` and `GPU{value}`, but writes only when the corresponding cached value exists and the selected 115200-baud port is open; because the two tasks are not ordered, it may reuse the previous sample. [Program.cs](/uploads/projects/juanyun-public/diy-cooling/desktop-program.cs) only starts the form, and the project file targets .NET Framework 4.7.2.

桌面端小到可以沿着一个源码文件读完。[Form1.cs](/uploads/projects/juanyun-public/diy-cooling/desktop-form1.cs)通过 LibreHardwareMonitor 查找 CPU 与 GPU 温度传感器；WinForms 定时器每 5000 ms 分别调度一次温度扫描与发送任务。发送端轮流检查 `CPU{value}` 和 `GPU{value}`，但只有对应缓存值存在、选中的 115200 波特率串口也已打开时才真正写出；两个任务没有先后保证，因此也可能复用上一次样本。[Program.cs](/uploads/projects/juanyun-public/diy-cooling/desktop-program.cs)只负责启动窗体，工程文件则把目标框在 .NET Framework 4.7.2。

At the other end, the [ESP32 source](/uploads/projects/juanyun-public/diy-cooling/esp32-platformio-main.cpp) uses `BluetoothSerial`, accepts those same two prefixes, and displays the current readings beside mode, duty cycle, and PWM frequency on a 128 × 64 SSD1306 OLED. Its initial PWM setup is 15 kHz, 8-bit resolution, and GPIO 5. The PlatformIO `.cpp` and Arduino `.ino` in the archive are byte-identical, so they are two filenames for one implementation rather than independent versions. The declared one-second long-press path is also empty in this code.

另一端的 [ESP32 源码](/uploads/projects/juanyun-public/diy-cooling/esp32-platformio-main.cpp)使用 `BluetoothSerial`，正好接收这两个前缀，再把当前读数与模式、占空比、PWM 频率一起显示在 128 × 64 的 SSD1306 OLED 上。PWM 初始配置是 15 kHz、8 位分辨率与 GPIO 5。归档里的 PlatformIO `.cpp` 和 Arduino `.ino` 逐字节相同，所以它们只是同一份实现的两个文件名，不是两套相互印证的版本。代码虽然声明了 1 秒长按分支，处理函数里却还没有逻辑。

## The Video Makes the Interface Chain Visible / 视频把接口链放到了同一段画面里

The 3:57 [desktop demo](/uploads/projects/juanyun-tech/diy-cooling-desktop-demo.mp4) moves from an installer and Windows discovering `ESP32_Bluetooth`, to a Hardware Monitor window with CPU/GPU values and COM-port selection, and then to a physical acrylic-and-foam prototype. Its OLED shows `Quiet`, `Normal`, and `Manual` modes, a 15000 Hz frequency, changing temperature values, and duty-cycle changes while the front buttons are pressed.

3 分 57 秒的[桌面端演示](/uploads/projects/juanyun-tech/diy-cooling-desktop-demo.mp4)从安装界面和 Windows 发现 `ESP32_Bluetooth` 开始，随后出现带 CPU / GPU 数值与 COM 口选择的 Hardware Monitor 窗口，最后镜头转到一台亚克力与泡棉结构的实体原型。OLED 上能看到 `Quiet`、`Normal`、`Manual` 模式、15000 Hz 频率、变化的温度值，以及按动前面板按钮时变化的占空比。

That sequence makes the intended interface chain more than a pair of matching source files. It is still a visible demonstration, not a serial packet log or a controlled thermal test. The [control note](/notes/juanyun-diy-cooling) follows the less obvious timing inside the code: the desktop schedules a conditional send attempt every five seconds, while the ESP32 waits for a 30-second maximum before revising automatic PWM.

这段连续画面让接口链不再只是“两份代码刚好对得上”，但它仍是可见演示，不是串口报文日志，更不是受控热测试。[控制笔记](/notes/juanyun-diy-cooling)继续追代码里更容易忽略的节拍：桌面端每五秒调度一次有条件的发送尝试，ESP32 却要等 30 秒峰值窗口结束，才改一次自动 PWM。

## A Later STM32 Archive Changes the Board Boundary / 后来的 STM32 归档换了板卡边界

The public electronics files contain two distinct snapshots. The earlier [schematic PDF](/uploads/projects/juanyun-public/diy-cooling/pcb-schematic.pdf), [EasyEDA project](/uploads/projects/juanyun-public/diy-cooling/easyeda-2024-project.epro), and [Gerber package](/uploads/projects/juanyun-public/diy-cooling/pcb-gerber.zip) are organized around an ESP32 development board, fan/PWM connectors, 12 V conversion, OLED, and five buttons. File presence proves that design and fabrication outputs were exported; it does not prove fabrication or board bring-up.

公开电子文件里能分出两个不同快照。较早的[原理图 PDF](/uploads/projects/juanyun-public/diy-cooling/pcb-schematic.pdf)、[EasyEDA 工程](/uploads/projects/juanyun-public/diy-cooling/easyeda-2024-project.epro)与 [Gerber 包](/uploads/projects/juanyun-public/diy-cooling/pcb-gerber.zip)围绕 ESP32 开发板、风扇 / PWM 接口、12 V 变换、OLED 与五个按键展开。文件存在能证明设计与制造输出已经导出，却不能替代打板和 bring-up 记录。

The later-dated render shows an STM32 module outline surrounded by two fan connectors, a 12 V input and power-conversion area, a USB-C interface area, Bluetooth and OLED headers, and five adjustment buttons. The schematic separately identifies the module as `STM32F103C8T6`, labels U14 as `CH340N`, and groups the USB data path, 12 V-to-5 V conversion, fan outputs, and the same central module and headers. The two artifacts agree on the shared connectors, module outline, and buttons, but the archive does not establish why the controller changed or how this board relates to the earlier physical demo.

日期更晚的渲染图里，STM32 模块轮廓周围排着两路风扇接口、12 V 输入与电源变换区域、USB-C 接口区域、蓝牙和 OLED 排针，以及五个调节按键。原理图才把模块准确标成 `STM32F103C8T6`，并将 U14 标成 `CH340N`，再展开 USB 数据路径、12 V 转 5 V、风扇输出，以及同一组中央模块与排针。两份材料只能在共同可见的连接器、模块轮廓与按键上互相对应；归档没有说明为什么更换主控，也没有交代这块板与前面实体演示之间的确切版本关系。

## A Temperature Number Is Not a Cooling Curve / 温度数字还不是散热曲线

The archive reaches a useful prototype boundary: prepared duct geometry, a desktop temperature sender, ESP32-side PWM/OLED logic, a visible physical demo, and two board-design snapshots can all be inspected together. What it does not contain is the evidence needed to judge cooling: no before/after temperature curves, air-pressure or flow readings, noise or power measurements, steady-state thermal comparison, or controlled workload record.

这组归档已经抵达一个很具体的原型边界：风道几何的打印准备、桌面温度发送端、ESP32 侧 PWM / OLED 逻辑、一段实体演示，以及两套板卡设计快照可以放在一起读。它没有抵达的，是判断散热效果所需的证据：没有温度前后曲线、风压 / 风量、噪声、功耗、稳态热对比，也没有受控负载记录。

The OLED temperature and duty-cycle values show what the controller was displaying. They do not reveal how much heat the duct removed. That question begins with a repeatable test setup, not another render.

OLED 上的温度与占空比能说明控制器当时显示了什么，却还说明不了风道带走了多少热量。这个问题的下一步应该是一套可重复的测试条件，而不是再添一张渲染图。
