## One Main Loop, Five Cadences / 一个主循环，五档节拍

The existing public note does not expose source files, but it does preserve a clear schedule. Electronic-expansion-valve work is assigned a 1 ms cadence; FG maintenance and encoder/key input sit at 10 ms; NTC updates at 100 ms; OLED refresh at 500 ms; and DHT22 reads at 2000 ms.

既有公开笔记没有展开源码，却保留了一张很清楚的节拍表：电子膨胀阀任务放在 1 ms，FG 维护与编码器 / 按键输入放在 10 ms，NTC 更新是 100 ms，OLED 刷新是 500 ms，DHT22 读取则是 2000 ms。

| Cadence | Responsibility |
| --- | --- |
| `1 ms` | Electronic expansion valve stepping |
| `10 ms` | FG maintenance, encoder/key scan, UI input |
| `100 ms` | NTC update |
| `500 ms` | OLED refresh |
| `2000 ms` | DHT22 read |

| 节拍 | 职责 |
| --- | --- |
| `1 ms` | 电子膨胀阀步进 |
| `10 ms` | FG 维护、编码器 / 按键扫描与 UI 输入 |
| `100 ms` | NTC 更新 |
| `500 ms` | OLED 刷新 |
| `2000 ms` | DHT22 读取 |

Read as a main-loop map, the table keeps fast actuator work away from slow environmental sensing. It also exposes a practical pressure point: a blocking operation in a slow path can still delay a faster responsibility if the loop has no stronger scheduling mechanism. The excerpt gives intended intervals, not measured jitter or deadline evidence.

把表格当作主循环地图看，快速执行器任务与慢速环境采样被分到了不同档位；它也顺手暴露一个很实际的压力点——如果慢路径里出现阻塞，而循环又没有更强的调度机制，快任务一样可能被拖住。这里记录的是预期间隔，不是抖动实测或 deadline 证明。

## `Core`, `App`, `Service`, and `BSP_drivers` Name the Boundaries / 四个目录名先划开职责

The same record names four layers: `Core`, `App`, `Service`, and `BSP_drivers`. `Core` is associated with the generated STM32 project, while application scheduling and reusable peripheral-facing work are separated into the other directories. The names are enough to express an intended boundary, although the files behind them are not linked here.

同一份记录给出四层目录名：`Core`、`App`、`Service` 与 `BSP_drivers`。`Core` 对应生成的 STM32 工程，其余目录把应用调度与可复用的外设侧工作分开。只看目录名已经能读出预期边界，但目录里的文件并未公开链接。

Two optimizations are described beside the schedule. OLED refresh can be skipped when display content is unchanged, reducing repeated I2C traffic and formatting. The NTC lookup is described as moving from a linear search to binary search. Both ideas target repeated work inside periodic paths; without a trace or benchmark, their timing effect remains unknown.

节拍旁边还写了两项优化：OLED 内容没变化时跳过刷新，减少重复 I2C 传输与格式化；NTC 查表则从线性搜索改成二分搜索。两项都在削减周期路径里的重复工作，但没有 trace 或 benchmark，实际省下多少时间仍然未知。

## Communication Labels Do Not Supply the Protocol Code / 通信标签补不出协议代码

The V2.1 ACUnit map labels compressor Modbus UART, ESP-01S Wi-Fi, HC-05 Bluetooth, and an ST-Link SWD port around the main board. Those labels identify firmware-facing surfaces. They do not reveal UART framing, retry behavior, module commands, fault handling, or the OpenOCD flashing sequence.

V2.1 ACUnit 接口图在主控板周围标出压缩机 Modbus UART、ESP-01S Wi-Fi、HC-05 蓝牙与 ST-Link SWD。这些标签能定位固件要面对的接口，却不会自动补出 UART 帧、重试策略、模块命令、故障处理或 OpenOCD 烧录过程。

The schedule is therefore the most concrete part of the record. It shows how control, sensing, display, and input were meant to take turns in one firmware structure. Source listings, serial logs, valve traces, and on-target timing measurements would be needed to say how that structure behaved on hardware.

因此，节拍是这份记录里最具体的一层：它说明控制、传感、显示与输入准备怎样在同一套固件结构里轮流工作。要判断这套结构在硬件上表现如何，还需要源码清单、串口日志、阀动作曲线与目标板时序测量。
