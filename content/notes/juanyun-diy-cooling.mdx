## `CPU62.7` Is the Whole Message / `CPU62.7` 就是整条报文

`CPU62.7` is short enough to look as if the protocol had not quite arrived for work. In this archive, however, that prefix and number are the entire bridge between the Windows monitor and the ESP32.

`CPU62.7` 只有几个字符，短得像协议还没来得及正式上班。可在这份归档里，桌面监控端与 ESP32 之间的桥，确实就是这个前缀加数值。

The [Windows form source](/uploads/projects/juanyun-public/diy-cooling/desktop-form1.cs) asks LibreHardwareMonitor for CPU and GPU temperature sensors and rounds each available value to one decimal place. The archived [desktop entry point](/uploads/projects/juanyun-public/diy-cooling/desktop-program.cs) launches that form inside the accompanying [.NET Framework project](/uploads/projects/juanyun-public/diy-cooling/desktop-cpuwenduhuoqu.csproj). Its WinForms timer fires every 5000 ms and schedules separate monitor and send tasks. On even counts, the send task checks whether a cached CPU value exists before attempting a `CPU{value}` line; odd counts do the same for `GPU{value}`. The helper reaches `SerialPort.WriteLine` only when the selected port exists and is open at 115200 baud.

[Windows 窗体源码](/uploads/projects/juanyun-public/diy-cooling/desktop-form1.cs)通过 LibreHardwareMonitor 查找 CPU 与 GPU 温度传感器，再把可用读数四舍五入到一位小数。归档中的[桌面程序入口](/uploads/projects/juanyun-public/diy-cooling/desktop-program.cs)在配套的 [.NET Framework 项目](/uploads/projects/juanyun-public/diy-cooling/desktop-cpuwenduhuoqu.csproj)内启动这个窗体。WinForms 定时器每 5000 ms 触发一次，并分别调度温度扫描与发送任务。偶数拍只有在 CPU 缓存值存在时才尝试写出 `CPU{value}`，奇数拍对 `GPU{value}` 做同样检查；辅助函数还要确认选中的 115200 波特率串口已经存在且打开，才会走到 `SerialPort.WriteLine`。

One detail changes how fresh that message can be. Each timer tick launches monitoring and sending in two separate `Task.Run` calls, without waiting for the sensor scan to finish before reading the shared temperature fields. The outgoing line is therefore not guaranteed to contain the sample started on the same tick; it may use the last stored value. The archive contains no timestamped log to show which ordering occurred during the demo.

这里有个细节，会影响“这一行到底有多新”。每次 timer tick 把温度扫描和串口发送分别塞进两个 `Task.Run`，发送前没有等待本轮扫描结束，而是直接读取共享温度变量。因此，发出去的不一定是同一拍刚采到的值，也可能是上一次留下的读数。归档里没有带时间戳的日志，无法还原演示时究竟是哪种先后顺序。

## Alternating Prefixes Give Each Sensor About Ten Seconds / 前缀轮流出现，每个传感器约十秒一拍

Each five-second timer event schedules one send attempt and alternates which prefix it considers. When the cached-value and open-port checks pass, successive attempts nominally give each sensor one opportunity every ten seconds. The [ESP32 source](/uploads/projects/juanyun-public/diy-cooling/esp32-platformio-main.cpp) reads through `BluetoothSerial` until `\n`, checks `startsWith("CPU")` or `startsWith("GPU")`, and converts the remaining text with `toFloat()`. The same folder also preserves the [PlatformIO configuration](/uploads/projects/juanyun-public/diy-cooling/esp32-platformio.ini) and a [byte-identical Arduino sketch copy](/uploads/projects/juanyun-public/diy-cooling/esp32-arduino-pwm-control.ino) of that source.

每个五秒定时事件只调度一次发送尝试，并轮换本次检查哪个前缀。缓存值存在且串口已打开时，连续尝试名义上给每个传感器约十秒一次的发送机会。[ESP32 源码](/uploads/projects/juanyun-public/diy-cooling/esp32-platformio-main.cpp)通过 `BluetoothSerial` 一直读到 `\n`，再用 `startsWith("CPU")` 或 `startsWith("GPU")` 分流，最后把后半段交给 `toFloat()`。同一目录还保留了 [PlatformIO 配置](/uploads/projects/juanyun-public/diy-cooling/esp32-platformio.ini)，以及与该源码[逐字节一致的 Arduino sketch 副本](/uploads/projects/juanyun-public/diy-cooling/esp32-arduino-pwm-control.ino)。

The current value goes to the OLED, but a second pair of variables keeps only the largest CPU and GPU readings seen so far. Every 30000 ms, the loop selects the larger of those two maxima, calls `updatePWM()`, and then clears both maxima for the next window. A 30-second window therefore contains roughly three opportunities per sensor under the nominal sender cadence. Missing lines, task ordering, and Bluetooth timing can change that count; no receive log is present to measure it.

当前值直接送去 OLED，旁边还有一组变量只保留窗口内见过的 CPU 与 GPU 最大值。每到 30000 ms，主循环从两个峰值里再挑较大的一个，调用 `updatePWM()`，随后把两边峰值清零，等待下个窗口。按名义发送节拍算，一个 30 秒窗口里每个传感器大约有三次机会。漏发、任务先后与 Bluetooth 时序都可能改掉这个数，而材料里没有接收日志可以核对。

This explains why the current temperature text and the PWM duty shown together on the OLED are not required to describe the same instant. One is the latest parsed line; the other can be the result of the largest value retained across the preceding window.

这也解释了为什么 OLED 上同时出现的“当前温度”与 PWM 占空比，不必属于同一个瞬间：前者是最近解析的一行，后者可能来自前一个窗口里保留下来的最大值。

## The Maximum Becomes a Duty Percentage Without a Setpoint / 峰值没有经过设定温度，直接变成占空比

`processBluetoothValue()` applies four simple mode rules. `Quiet` multiplies the selected maximum by 0.5, `Normal` by 0.7, and `high speed` uses it directly. `Manual` keeps the current duty cycle. The result is then mapped from a nominal 0–100 percentage to the 8-bit LEDC range used on GPIO 5 at an initial 15 kHz.

`processBluetoothValue()` 对四种模式做的是直接换算：`Quiet` 把选中的峰值乘 0.5，`Normal` 乘 0.7，`high speed` 原样使用，`Manual` 则保留当前占空比。结果随后从名义上的 0–100% 映射到 8 位 LEDC 范围，初始输出在 GPIO 5、15 kHz。

There is no target temperature, error term, hysteresis, fan-tachometer feedback, pressure input, or airflow measurement in this control path. Automatic results are also not explicitly clamped to 0–100 before `map()`, and the floating-point maximum is passed through an integer function parameter. The code is best read as a temperature-number-to-duty rule, not a closed-loop thermal controller.

这条控制路径里没有目标温度、误差项、滞回、风扇转速反馈、压力输入或风量测量。自动模式的结果在进入 `map()` 前也没有显式限制到 0–100，浮点峰值还会先经过整型函数参数。更准确的叫法，是“温度数字到占空比的规则”，而不是闭环温控器。

The five short-press actions share the same updater: one cycles the mode, two change frequency by 200 Hz, and two adjust manual duty by 10 percentage points. Every short press ends by calling `updatePWM()`. A press held for at least one second takes a separate long-press branch, but that handler is empty in the archived source. The interface visibly has five buttons; the code does not support a completed long-press feature.

五个短按动作最后共用同一个更新函数：一个轮换模式，两个以 200 Hz 步长加减频率，两个在手动模式下以 10 个百分点加减占空比。每次短按收尾都会调用 `updatePWM()`。按住至少一秒会进入另一条长按分支，但归档源码里的处理函数是空的。前面板确实有五个按钮，代码却还没有完成长按功能。

## The Demo Shows the Chain, Not the Thermal Result / 演示看得到链路，看不到散热结论

The 3:57 [demo video](/uploads/projects/juanyun-tech/diy-cooling-desktop-demo.mp4) places several pieces in one sequence: Windows discovers `ESP32_Bluetooth`, the Hardware Monitor window displays CPU/GPU values and a COM-port list, and the physical prototype OLED shows temperature values, 15000 Hz, and `Quiet`, `Normal`, or `Manual` while the front buttons are used. That is useful visible evidence for the intended interface chain.

3 分 57 秒的[演示视频](/uploads/projects/juanyun-tech/diy-cooling-desktop-demo.mp4)把几块线索放进了同一段连续画面：Windows 发现 `ESP32_Bluetooth`，Hardware Monitor 窗口显示 CPU / GPU 数值与 COM 口列表，实体原型的 OLED 则在按动前面板按钮时显示温度、15000 Hz，以及 `Quiet`、`Normal` 或 `Manual`。它为预期接口链提供了很有用的可见证据。

It is not a packet trace. It also contains no controlled workload, synchronized temperature curve, fan waveform, pressure or flow reading, acoustic result, or power measurement. The text protocol and 30-second maximum strategy explain the control intent; timestamped transmit/receive logs and PWM captures would be needed to explain timing behavior, and a repeatable thermal test would still be needed to explain cooling effect.

但它不是报文 trace，也没有受控负载、同步温度曲线、风扇波形、风压 / 风量、噪声或功耗数据。文字协议与 30 秒峰值策略已经足够解释控制意图；要解释时序行为，还得补带时间戳的收发日志与 PWM 捕获；要解释散热效果，则仍然要从可重复的热测试开始。
