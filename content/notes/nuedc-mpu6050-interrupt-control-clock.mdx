SysConfig in the car's project defines a periodic timer, `TIMER_0`, set to exactly 5 ms. Nothing ever starts it. The 5 ms tick that actually drives the car comes from somewhere else: inside `GROUP1_IRQHandler`, below the two encoder handlers, sits a branch for the MPU6050's interrupt pin, and the comment there says the frequency is configured through the DMP, 200 Hz by default. That branch reads the sensor, then calls `BalanceControlTask()`, and the comment under it says a correct `mainTaskFreq` should equal 200. The structure came with the balance-car example the code started from, where reading attitude and balancing in the same breath makes obvious sense. On a line-tracking car, it means the motor control keeps time by an IMU.

小车工程的 SysConfig 里配了一个周期定时器 `TIMER_0`，周期正好 5 ms，可代码里从来没有启动它。真正给车打拍子的 5 ms 来自别处：`GROUP1_IRQHandler` 里，两路编码器的处理下面，是 MPU6050 中断引脚的分支，注释写着频率可以通过 DMP 配置，默认 200 Hz。这个分支先读传感器，再调用 `BalanceControlTask()`，下面还有一句注释，说频率正确的话 `mainTaskFreq` 应该等于 200。这套结构是从代码起步时用的平衡车例程里带过来的，平衡车读完姿态立刻做平衡，放在一起顺理成章；放到循迹小车上，就成了电机控制靠一个陀螺仪来掐表。

## DMP Data-Ready at 200 Hz / 200 Hz 的 DMP 数据就绪中断

`DMP_Init()` sets both the MPU6050's sample rate and the DMP's FIFO rate to `DEFAULT_MPU_HZ`, which is 200. Each time the DMP drops a new packet into its FIFO, it pulls the INT pin low, and the MSPM0 pin wired to it, PA7, is configured with a pull-up and a falling-edge interrupt. The 5 ms period therefore comes from the MPU6050's own clock, independent of how busy the MSPM0 is. People who have tried to slow the interrupt down on the InvenSense forum found that it [stays at 200 Hz](https://adm.invensense.tdk.com/comment/12763) because the motion driver library fixes the DMP's internal sample rate, so this rate is also the natural one to build on.

`DMP_Init()` 把 MPU6050 的采样率和 DMP 的 FIFO 输出率都设成 `DEFAULT_MPU_HZ`，也就是 200。DMP 每往 FIFO 里放一包新数据，就把 INT 引脚拉低；MSPM0 这边接 INT 的是 PA7，配成上拉、下降沿触发。这样一来，5 ms 的周期出自 MPU6050 自己的时钟，跟 MSPM0 忙不忙没有关系。InvenSense 论坛上有人想把这个中断调慢，发现它[始终停在 200 Hz](https://adm.invensense.tdk.com/comment/12763)，因为 motion driver 库把 DMP 内部的采样率写死了，所以 200 Hz 也正好是最顺手的拍子。

Inside the branch, `Read_DMP()` pulls the packet over hardware I2C on PA0 and PA1, turns the quaternion into roll, pitch and yaw, and stores them in the `mpu6050` structure. On this car, nothing in the control path uses those angles. The steering and speed loops work entirely from encoder counts. The only place attitude shows up is the OLED: about 100 s after boot the code takes one snapshot of yaw, and from then on the screen shows how far the car has turned from it and which quadrant the nose points into. The assignments carry small traces of the example too: pitch is filled from `Roll`, roll from `Pitch`, and all three acceleration axes from `accel[0]`. They do no harm here, since nothing in the control path looks. In this car the MPU6050's main job turns out to be a metronome.

分支里，`Read_DMP()` 通过 PA0、PA1 上的硬件 I2C 把这包数据读出来，把四元数换算成横滚、俯仰、偏航，存进 `mpu6050` 结构体。这辆车上，控制链路里没有任何地方用到这几个角度：转向环和速度环全靠编码器读数。姿态唯一露面的地方是 OLED：开机大约 100 秒后拍下一次偏航角，之后屏幕上显示车相对它转了多少度、车头朝哪个象限。赋值的地方还留着例程的小痕迹：pitch 拿的是 `Roll`，roll 拿的是 `Pitch`，三个轴的加速度全从 `accel[0]` 取。控制链路里没人看，也就不碍事。说到底，这颗 MPU6050 在这辆车上最主要的活儿，是当节拍器。

## Halving to 100 Hz / 减半到 100 Hz

`BalanceControlTask()` runs on every interrupt but does the real work on every other one. Every call checks the user key and reads the battery voltage from the ADC. A variable `controlFlag` flips each call, and only on alternate calls does the task read both encoder counters, zero them, compute wheel speed, run the speed and steering loops and write the PWM. Control therefore runs at 100 Hz, and each encoder count covers a 10 ms window. The speed formula in `balance.h` is built on that: `Control_Frequency` is 100, the encoder has 13 lines, the gearbox is 30 to 1 and the decoding is 2x, so one wheel revolution is 2 × 30 × 13 = 780 counts, and a count of n in 10 ms means n / 7.8 revolutions per second.

`BalanceControlTask()` 每次中断都会进来，但隔一次才真正干活。每次进来都会查一下用户按键、读一下 ADC 上的电池电压；变量 `controlFlag` 每次翻转一下，只有隔一次的那一半，才去读两路编码器的计数、清零、算轮速、跑速度环和转向环、写 PWM。所以控制频率是 100 Hz，每次读到的编码器计数覆盖 10 ms。`balance.h` 里的轮速公式就建在这上面：`Control_Frequency` 是 100，编码器 13 线，减速比 30 比 1，二倍频解码，轮子转一圈是 2 × 30 × 13 = 780 个计数，10 ms 里读到 n 个计数，就是每秒 n / 7.8 圈。

## Encoder Decoding at 2x / 编码器的二倍频解码

The encoders are quadrature encoders: two channels, A and B, a quarter of a cycle apart, so the level of one channel at an edge of the other tells you which way the wheel is turning. Counting only rising edges of A gives one count per cycle, counting every edge on both channels gives four, the usual [x1, x2 and x4 decoding](https://en.wikipedia.org/wiki/Incremental_encoder). This code enables interrupts on the rising edges of both A and B. On a rising edge of A, B high means one direction and B low the other; on a rising edge of B, the rule is mirrored using A. Two counts per cycle, hence the 2 in the formula. Each edge costs one trip into `GROUP1_IRQHandler`.

编码器是正交编码器：A、B 两路信号相差四分之一个周期，在一路的边沿上看另一路的电平，就知道轮子往哪边转。只数 A 的上升沿，一个周期记一次；两路的每个边沿都数，一个周期记四次，这就是常说的 [x1、x2、x4 解码](https://en.wikipedia.org/wiki/Incremental_encoder)。这份代码对 A、B 两路的上升沿都开了中断：A 上升时，B 是高就往一个方向记，B 是低就往另一个方向记；B 上升时，拿 A 的电平按镜像的规则判断。一个周期记两次，公式里那个 2 就是这么来的。每个边沿都要进一趟 `GROUP1_IRQHandler`。

## Sharing One Interrupt / 共用一个中断

The encoders and the MPU6050 interrupt all land in the same handler, and that is where the cost of this design shows. While the handler is busy with `Read_DMP()`, an I2C transfer, and then the control task, a new encoder edge sets its pending flag and waits. One waiting edge is fine; the flag remembers it. If the same pin produces a second edge before the handler gets back to it, the two collapse into one pending flag and a count is lost. A comment in `main` says as much: with software I2C, the DMP read was too slow and interfered with the encoder interrupts, which is why the project uses the hardware I2C peripheral on PA0 and PA1. The project also carries a debug timer counting at 100 kHz, and the handler uses it to measure both how often it runs and how long each run takes, `mainTaskFreq` and `mainTaskUseTime`, which is exactly the pair of numbers this design needs watching.

编码器和 MPU6050 的中断都落进同一个处理函数，这个方案的代价就在这里。处理函数正忙着跑 `Read_DMP()` 的 I2C 传输、接着跑控制任务的时候，新来的编码器边沿只能先把挂起标志置上，排队等着。等一个边沿没关系，标志会记住它；同一个引脚要是在处理函数回来之前又来了第二个边沿，两个边沿就并成一个挂起标志，丢一个计数。`main` 里有一句注释说的正是这件事：用软件 I2C 时，DMP 读得太慢，会影响编码器中断。所以工程里用的是 PA0、PA1 上的硬件 I2C 外设。工程里还带了一个 100 kHz 计数的调试定时器，处理函数拿它同时测自己多久跑一次、每次跑多久，也就是 `mainTaskFreq` 和 `mainTaskUseTime`，这套设计要盯的恰好就是这两个数。

There is one more consequence that only shows up when thinking about failure. `set_pwm()` is called only from inside the control task. If the MPU6050 ever stopped raising its interrupt, through a loose wire or a stuck I2C bus, the control loop would simply stop running, and the timer would go on producing the last duty cycle it was given. The car would keep driving at whatever PWM it had at that moment, with no tracking and no stop. The I2C driver does have a 10 ms timeout that unlocks a stuck SDA line, which keeps a hung transfer from freezing the handler, but nothing watches for the interrupt not arriving at all. A sensor-driven clock is precise and costs no timer, and the whole drive depends on that one sensor staying alive.

还有一个后果，要从出故障的角度想才看得到。`set_pwm()` 只在控制任务里被调用。如果 MPU6050 哪天不再发中断，比如线松了，或者 I2C 总线卡死，控制环就直接停了，而定时器会继续输出最后一次给它的占空比。车会按那一刻的 PWM 一直开下去，不循迹，也不停。I2C 驱动里倒是有 10 ms 超时，超时就去解锁卡住的 SDA，能防止一次卡住的传输把处理函数冻住，可没有任何东西在盯着中断根本没来这件事。用传感器当时钟，拍子准，还省一个定时器；整辆车跑不跑得动，也就系在这一颗传感器身上。
