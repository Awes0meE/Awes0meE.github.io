## GPIO Answers “What Level Is It Now?” / GPIO 回答“现在是什么电平”

The first excerpt shows the state model in its simplest form. GPIOC pin 13 is configured as a push-pull output, then explicitly set and reset. For an input, the direction reverses: software reads a level that already exists outside the MCU. Either way, GPIO describes a state at the moment it is accessed.

第一段摘录把状态模型写得很直接：GPIOC13 配成推挽输出，然后被明确置位、复位。换成输入时，方向反过来——软件读取 MCU 外部已经存在的电平。无论输入还是输出，GPIO 回答的都是访问那一刻的状态。

This matters because a level and an event are not interchangeable. Repeatedly reading a high level tells the program that the signal remains high; it does not by itself identify the instant when the signal changed.

这里最关键的区别是，电平和事件不能互换。反复读到高电平，只能说明信号仍然为高；它本身并没有指出信号在哪一刻发生了变化。

## EXTI Turns a Selected Edge Into an Event / EXTI 把指定边沿变成事件

The environment-demo excerpt calls `Encoder_EXTI_Config()` before entering its loop, then consumes `Get_Encoder_Value()` while calculating `set_light_value`. These are two visible positions—a configuration entry and a value-consumption point—not a complete event chain.

环境 demo 在进入循环前调用 `Encoder_EXTI_Config()`，主循环随后在计算 `set_light_value` 时消费 `Get_Encoder_Value()`。这是两个可见位置——一个配置入口和一个数值消费点——还不是完整的事件链。

The public files do not include the interrupt handler, edge selection, direction decoding, or the code that updates the encoder count. The function names locate where to inspect next, but they do not establish which handler or edge produced the consumed value.

公开文件没有中断服务函数、边沿选择、方向判定，也没有更新编码器计数的代码。函数名能提示下一步该检查哪里，却不能确认消费到的数值由哪个 handler 或哪种边沿产生。

The linked encoder-servo excerpt begins at the consumer: it reads `encoder_count` and turns that value into an output command. It identifies where the count is used, not the handler or edge that updates it: [encoder count consumer excerpt](/uploads/projects/tianjin-metro/encoder-servo-speed-excerpt.c).

链接中的编码器—舵机摘录从消费端开始：代码读取 `encoder_count`，再把这个值变成输出指令。它说明计数在哪里被使用，却不能补出更新计数的 handler 或边沿：[编码器计数消费端摘录](/uploads/projects/tianjin-metro/encoder-servo-speed-excerpt.c)。

## Timers Answer “When Should It Happen Again?” / Timer 回答“下一次何时发生”

A timer introduces a third question. GPIO gives a level and EXTI marks a transition; a timer counts from a clock so that work can be paced or a waveform can repeat. The integration excerpt initializes both `TIM3_Config()` and `TIM4_PWM_Config()`, separating a general timing setup from the timer configuration used for PWM output.

定时器又带来第三个问题。GPIO 给出电平，EXTI 标记变化；Timer 从时钟计数，让任务获得节奏，也让波形可以重复。综合摘录同时初始化 `TIM3_Config()` 与 `TIM4_PWM_Config()`，把一般计时配置和 PWM 所需的定时器配置放在了两个入口。

The excerpt does not show TIM3's callback or connect TIM3 to a particular flag or interval. It records the configuration entry only. TIM4 has a separate PWM configuration entry and a public channel-1 compare write, but its counter period and update timing are not exposed here.

摘录没有展开 TIM3 回调，也没有把 TIM3 与某个 flag 或周期连接起来；这里能看到的只有配置入口。TIM4 另有 PWM 配置入口和公开的通道 1 比较值写入，但计数周期与更新时间同样没有在这里展开。

That distinction changes the next debugging question. For GPIO, inspect the level and direction; for EXTI, inspect the selected edge and handler; for a timer, inspect its clock, counter, and update event. Seeing the three initialization names together does not make their mechanisms interchangeable.

这个区别会直接改变下一步的调试问题：GPIO 要看电平和方向，EXTI 要看选中的边沿与 handler，Timer 要看时钟、计数器和更新事件。三个初始化名称出现在同一工程里，也不会让三种机制变成一回事。
