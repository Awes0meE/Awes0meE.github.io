## qmake Passed, but the Kit Still Did Not Match / qmake 过了，Kit 还是没配对

Week one began with what looked like an installation checklist: Git, MSVC v142, a Windows SDK, Qt Creator, CDB, and a Qt kit. The first choice was Qt 5.15.2. Making `core5compat` conditional allowed qmake to finish, which briefly looked like progress, until the full build produced more than thirty errors from Qt6-side APIs and headers in the current Seamly2D branch.

第一周开始时，环境看上去像一张安装清单：Git、MSVC v142、Windows SDK、Qt Creator、CDB，再选一个 Qt Kit。最初选的是 Qt 5.15.2；把 `core5compat` 改成条件加载以后，qmake 顺利结束，场面一度很乐观。然后完整构建扔出三十多个 Qt6 侧 API 与头文件错误，提醒我“工程文件生成成功”跟“这套源码能编译”根本不是一句话。

Switching to Qt 6.5.3 MSVC2019 64-bit, selecting the v142 compiler, deleting the old build directory and `.pro.user`, and configuring the kit again made the parts line up. A later post-link failure at `windeployqt` exposed another hidden dependency: Qt Creator had a Run button, but the build environment still needed the correct Qt `bin` path and a Release-only deploy rule.

改到 Qt 6.5.3 MSVC2019 64-bit，选好 v142 编译器，删掉旧 build 目录与 `.pro.user`，再重新配置 Kit，几块拼图才对上。随后 post-link 又在 `windeployqt` 处停下：Qt Creator 虽然一直有绿色运行按钮，构建环境却仍要知道 Qt `bin` 在哪，部署规则也该只在 Release 阶段触发。

By the end of that bring-up, “the environment works” no longer meant that every installer had completed. It meant that the branch, Qt package, compiler toolset, architecture, paths, qmake step, and full build agreed with one another. The [week-one raw log](/uploads/projects/nanjing-turing/week-1-development-log.txt) is short; the longer [Qt6 first-run note](/notes/turing-qt-seamly2d-first-run) keeps the route through those mismatches.

这轮 bring-up 结束时，“环境能用”已经不再等于“每个安装器都点完了”，而是分支、Qt 包、编译器工具集、架构、路径、qmake 与完整构建终于彼此同意。[第一周原始日志](/uploads/projects/nanjing-turing/week-1-development-log.txt)很短，更完整的错配过程保留在 [Qt6 首跑笔记](/notes/turing-qt-seamly2d-first-run) 里。

## A Login Window Turned Rules into State Transitions / 一个登录窗口把规则变成了状态转换

The next part of week one added local registration and login before the upstream Seamly2D interface. The log records `QSettings` storage, a move from plaintext comparison to hash-based verification, masked password fields, and prompts for existing users, missing users, and incorrect passwords. Pressing Enter was changed from the cancel path to confirmation. The log separately says username input suggestions were disabled. It also records a password-field crash under a Chinese input method as fixed, while the public excerpt does not include that patch. Desktop UI had found a decidedly non-permission-shaped way to remind me that input state was part of the problem too.

第一周后半段在上游 Seamly2D 界面前接入本地注册与登录。日志记录了 `QSettings` 存储、从明文比较改到哈希校验、密码隐藏，以及用户已存在、用户不存在和密码错误提示；回车键也从取消改到确认。日志另记用户名输入关闭了联想与提示词。密码框在中文输入法下的闪退也被记为已修复，但公开摘录没有包含对应补丁。桌面 UI 有时确实会挑一条完全不像“权限问题”的路来提醒你，它也是状态的一部分。

Week two made that state explicit. The first account had to be named `admin`; administrators could see user management while normal users could not. Deletion required confirmation and applied only to normal users. Promotion also targeted normal users, while demotion was reserved for the `admin` account, preventing other administrators from demoting one another.

第二周把这些状态写得更明确：首次账号必须叫 `admin`；管理员看得到用户管理，普通用户看不到；删除前要确认，而且只能删除普通用户；升级也只针对普通用户；降级则只留给 `admin`，其他管理员不能互相降级。

At first these sounded like a list of buttons. In practice each action asks for the current user, target user, target role, allowed transition, cancellation path, and message. The [week-two raw log](/uploads/projects/nanjing-turing/week-2-development-log.txt) preserves that full sequence; the published excerpt isolates the local role lookup used at the application entrance.

刚读日志时，这些内容很像一串按钮；真正接进窗口后，每个动作都要回答当前用户是谁、目标用户是谁、目标角色是什么、这次转换能不能发生、能不能取消、提示该怎么说。[第二周原始日志](/uploads/projects/nanjing-turing/week-2-development-log.txt)按当时顺序保留完整规则，公开摘录则只截取应用入口处的本地角色查询。

## The Release Folder Added a Third Meaning of “Working” / Release 目录给“能跑”加了第三层意思

Week three opened with a `.sm2d` XML sample and a first pass at its data shape, then shifted to Release once the `develop` branch and the earlier features were running. Release made the toolchain questions return in a less forgiving form. Compiler-version conflicts, MSVC, CMake, Ninja, and Qt package discovery were studied together, even though the recorded Seamly2D build itself still followed qmake.

第三周先从 `.sm2d` XML 样例读起，初步观察数据结构；等 `develop` 分支与前两周功能跑通后，重心转向 Release。工具链问题马上以更不讲情面的方式回来：编译器版本冲突、MSVC、CMake、Ninja、Qt 包发现被放到一起补课，尽管这份 Seamly2D 构建记录本身仍走 qmake。

On Windows, the local chain reached a Release executable, Qt dependency collection with `windeployqt`, a manual `xerces-c_3_2.dll` copy, self-signing, an Inno Setup installer, installation, and launch on the same machine. That result was concrete, but narrower than “ready for distribution”: the workflow note says there was no clean Windows device without Visual Studio or Qt available for a second-machine test.

Windows 本机链路走到了 Release 可执行文件、`windeployqt` 收集 Qt 依赖、手动补 `xerces-c_3_2.dll`、自签名、Inno Setup 安装包、安装并在同一台机器启动。这个结果很具体，但比“已经可分发”窄得多：流程文档注明手头没有一台不装 Visual Studio 与 Qt 的干净 Windows 设备做第二台机器验证。

That distinction changed the meaning of the green Run button again. Debug inside Qt Creator, a Release executable in its build directory, a dependency-filled folder, and an installer that runs locally are four different checkpoints. The [week-three raw log](/uploads/projects/nanjing-turing/week-3-development-log.txt) compresses them into a timeline; the [Release packaging note](/notes/turing-release-packaging-cross-platform) keeps the Windows commands and the untested clean-machine boundary.

绿色运行按钮的含义因此又变了一次：Qt Creator 里的 Debug、构建目录里的 Release 可执行文件、收齐依赖的目录、本机能安装运行的安装包，是四个不同检查点。[第三周原始日志](/uploads/projects/nanjing-turing/week-3-development-log.txt)把它们压成时间线，[Release 打包笔记](/notes/turing-release-packaging-cross-platform)则保留 Windows 命令和未做干净机验证的边界。

## macOS Reopened the Signing Question / 到了 macOS，签名问题重新打开

Moving the Windows-side code to a Mac did not preserve the environment. Homebrew Qt and the official Qt installation differed in paths and architecture, so Debug was brought up first and Release was handled again. The unsigned script copies the Release `.app`, runs `macdeployqt`, and creates a compressed DMG with `hdiutil`; the weekly log records those non-signing steps as working.

把 Windows 侧代码移到 Mac，并不会顺便搬走原来的环境。Homebrew Qt 与官方 Qt 的路径、架构不同，只能先跑 Debug，再重新处理 Release。无签名脚本会复制 Release `.app`，用 `macdeployqt` 收依赖，再通过 `hdiutil` 创建压缩 DMG；周日志把这些不涉及签名的步骤记为已实现。

Signing stopped earlier. A self-signed certificate was created, and a second script lays out `codesign`, `spctl`, and DMG steps, but the log says the automation worked except for signing. There is no completed Apple signing or notarization result in the record. The script is useful because it shows the intended order; it does not turn that order into a finished release.

签名停得更早：自签名证书创建成功，第二份脚本也排好了 `codesign`、`spctl` 与 DMG 步骤，但日志明确写着自动化“除签注外功能均实现”。记录中没有完成 Apple 签名，更没有 notarization。脚本的价值在于把目标顺序写清楚，不会因为步骤都列在里面，就自动变成一次成功发布。

By the end of the third week, saying “it works” required one more noun: the source works with which Qt kit, the role transition works for which account, the package works on which machine, and the signature was checked by which platform service. That extra noun is the part of the log I would keep.

到第三周结束，“能跑”后面必须再补一个名词：源码配哪套 Qt Kit 能跑，角色转换对哪个账号能跑，安装包在哪台机器能跑，签名又经过哪个平台服务检查。这几个补语，才是三周日志里最值得留下的部分。
