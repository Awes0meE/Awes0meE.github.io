## The Real Conflict Was Between Two Device Assumptions / 真正冲突的是两套器件前提

The code was counting while the digits alternated between darkness and nonsense. I naturally suspected the Arduino program and my jumper wiring first; the course diagram seemed more trustworthy than my own judgment. But with the common pin grounded as shown, checking the BCD table again and again did not make the display behave.

代码明明在计数，数码管却时而全黑、时而乱码。我最初当然先怀疑 Arduino 程序和杜邦线，因为课件上的接法看起来比我的判断可靠。可我按图把公共端接地以后，无论怎么复查 BCD 表，显示都不肯正常工作。

![Course system structure / 课程中的系统结构拆分](/uploads/projects/arduino-digital-clock-counter/course-system-structure.png)
![TinkerCAD one-digit demo / TinkerCAD 一位归零计数 demo](/uploads/projects/arduino-digital-clock-counter/tinkercad-one-digit-demo.png)

I only found the correct datasheet while organizing this portfolio, and it finally gave the old symptom a clean explanation. TI describes the [SN74LS47](https://www.ti.com/product/SN74LS47) as an active-low, open-collector driver intended for common-anode LEDs. The [CD4511B](https://www.ti.com/lit/ds/symlink/cd4511b.pdf) used in the course simulation directly drives common-cathode LEDs. Both decode BCD for seven-segment displays. The CD4511 and LS47 drive opposite current paths. By treating the CD4511 as a close reference for the lab device, the slide stepped over exactly the difference most likely to stop a beginner cold.

我后来整理作品集时才找到正确的数据手册，也才把当年的现象说清楚。TI 对 [SN74LS47](https://www.ti.com/product/SN74LS47) 的说明是低有效、开集电极输出，用来直接驱动共阳 LED；课件仿真里的 [CD4511B](https://www.ti.com/lit/ds/symlink/cd4511b.pdf) 则能直接驱动共阴 LED。两者都负责把 BCD 译码成七段控制信号，各自驱动的电流路径相反。课件把 CD4511 当作接近实验器件的参考，恰好漏掉了最会让初学者卡死的差异。

![BCD decoder notes / BCD 到七段译码器说明](/uploads/projects/arduino-digital-clock-counter/bcd-decoder-notes.png)

## The Current Path Beyond Four BCD Bits / 四个 BCD bit 之外，还有电流路径

At the time, I had only just learned the logical part. `Num % 10` produced the units digit; `(Num / 10) % 10` produced the tens digit. Each result selected a BCD row and sent four bits to one decoder. That was enough to make the numbers move, but I had not yet connected those bits to decoder polarity, LED orientation, and the common-pin voltage in one mental picture.

当时我刚学会的只是逻辑关系。`Num % 10` 得到个位，`(Num / 10) % 10` 得到十位；两个结果各自查 BCD 表，再把四个 bit 写给两颗译码器。这个办法能让数字跑起来，但我脑子里还没有把它与译码器输出极性、LED 方向和公共端电位连成一张图。

Looking back, the four BCD bits select the number to display; current still needs a path to the LEDs. In the LS47 path, a low segment output sinks current. With the common-anode display tied to VCC, current can travel from VCC through an LED and its limiting resistor into the driver. Ground the common pin as if the display were common-cathode, and the software state can keep changing while the physical path is already broken. The fix looked almost magical at the time. Moving the common pin to VCC allowed current to flow.

现在回看，四位 BCD 负责选择要显示的数字，LED 还需要一条电流路径。对 LS47 这条链路来说，段输出拉低时负责吸收电流；共阳数码管的公共端接到 VCC 后，电流才能从 VCC 经过 LED 和限流电阻流向驱动器。公共端一旦按共阴方案接到 GND，代码里的数字仍在变化，物理链路却已经断了。把公共端改接 VCC 后显示恢复正常，是因为电流终于走通。

## A Multimeter Says More Than `...Pressed` / 万用表比 `...Pressed` 更接近真相

The six-pin self-locking switch repeated the same lesson. A variable can be named `switch1Pressed`, but the name says nothing about which of six pins connect before and after a press. Without a datasheet, I began by moving wires around. I saw no response, unstable readings, and sometimes two reactions to one press. Borrowing a multimeter and checking every pin pair for continuity turned that guesswork into a connection map I could actually verify.

六脚自锁按键把同一件事又演了一遍。变量可以叫 `switch1Pressed`，但它不会告诉我六只脚在按下前后怎样导通。没有数据手册时，我先靠换线试，遇到过没反应、读数乱跳和一次触发两次。后来我借来万用表，用通断测试把每一对引脚量过去，才把内部连接关系从猜测变成可以复查的结果。

![Button pull-up and pull-down notes / 按键上下拉说明](/uploads/projects/arduino-digital-clock-counter/button-pullup-notes.png)

I mapped the switch topology, and both pause and reset passed the classroom demonstration. The surviving report checks one switch with `HIGH`, another with `LOW`, and also mentions a pull-up, so its conflicting descriptions leave the final polarity unknown. A double trigger resembles ordinary mechanical contact bounce, and Arduino's [Debounce example](https://docs.arduino.cc/built-in-examples/digital/Debounce/) likewise waits for an input to remain stable before accepting a state change. The final source is gone, so the debounce implementation remains unknown and I will not claim that I used a particular algorithm.

我测出了开关拓扑，最终暂停和复位都通过了课堂演示。现存报告一处用 `HIGH` 判断，另一处用 `LOW`，文字又提到上拉，彼此冲突的描述无法还原最终极性；一次按压触发两次与机械触点抖动的典型表现相似，[Arduino 的 Debounce 示例](https://docs.arduino.cc/built-in-examples/digital/Debounce/) 也要求输入稳定一段时间后再承认状态变化。最终源码没有保存下来，消抖实现仍然未知，所以我不会声称当时已经采用了哪种算法。

## I Now Start by Asking Which Part Is Actually on the Bench / 我现在会先问，手里到底是哪颗器件

The original firmware advanced the count through polling and blocking `delay()` calls. That was enough for a simple counter, but it squeezed timing, display updates, and button handling into one loop. Arduino's own [`delay()` reference](https://docs.arduino.cc/language-reference/en/functions/time/delay/) warns that most other activity stops during the wait. This is a judgment I formed while looking back, not an architecture I understood during the project.

当年的程序主要靠轮询和阻塞式 `delay()` 推进计数。它足够让一个简单计数器跑起来，却把计时、显示更新和按键响应都挤在同一个循环里；[Arduino 对 `delay()` 的说明](https://docs.arduino.cc/language-reference/en/functions/time/delay/) 也明确提醒，等待期间大部分其他活动都会停下来。这是我现在回看才形成的判断，不是当时就有的架构意识。

![Milestone breakdown / 课程里程碑拆分](/uploads/projects/arduino-digital-clock-counter/milestone-breakdown.png)

If I met the same board now, I would identify the decoder and display common first, map the switch contacts with a multimeter, then verify one segment, one digit, and one button before integrating both display paths with the counter state. The slide provides a model, and the part on the bench determines where current can actually flow.

如果现在再遇到同样的板子，我会先确认器件型号和公共端，用万用表找出开关拓扑，再分别验证一个段、一位显示和一个按键，最后才把两条显示链与计数状态合起来。课件提供模型，台面上的器件决定电流实际往哪里走。

I began the project thinking it was an Arduino programming task. What stayed with me was a more practical debugging habit. Identify the part and measure how it conducts, then decide whether the code needs changing.

一开始，我以为这个项目就是一项 Arduino 编程任务。最后真正留下来的是一条更实用的调试习惯，先确认器件，再量它实际上怎样导通，再判断代码是否需要改。
