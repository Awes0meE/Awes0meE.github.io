## The Simpler Controller Was Still a Complete System / 相对简单，不等于只点亮几个外设

I chose to finish the BaseUnit before moving on to the ACUnit. The reason was not that it could be treated as a throwaway prototype. It already had every kind of responsibility that makes a controller feel complete. Sensors entered the system, a user changed state, a fan responded, the display reflected the current mode, telemetry left the board, and one setting had to survive a restart.

我决定先把 BaseUnit 做完，再去做 ACUnit。原因不是它可以随便当成一块过渡原型，而是它已经包含了一套控制器该有的完整责任。传感器把状态送进来，用户改变模式，风扇作出响应，屏幕映射当前状态，遥测离开板子，一个设定值还得跨过重启保留下来。

DHT11 measured the surrounding air, while DHT22 measured the outlet side. An infrared input represented whether the laptop was in position. The encoder selected a fan setting from 0 to 100 percent, and the OLED displayed `ENV`, `OUT`, and `FAN`. Those parts were not six independent demos. Presence, UI state, and the saved setpoint jointly decided whether the PWM output should exist at all.

DHT11 负责环境温湿度，DHT22 负责出风侧温湿度，红外输入表示笔记本是否在位，编码器把风扇设定调在 0 到 100%，OLED 再显示 `ENV`、`OUT` 与 `FAN`。这些并不是六个互不相干的外设 demo。在位状态、UI 状态和保存下来的设定值，要一起决定 PWM 此刻究竟该不该输出。

## A Black Screen Was One State, Not an Empty Display / 黑屏是一种状态，不是屏幕没内容

The application moved among `UI_OFF`, `UI_BOOT`, `UI_NORMAL`, and `UI_CONFIRM`. In the off and boot states, the fan stayed at zero. Boot displayed a logo before normal sensing and control began. A shutdown request did not immediately cut the interface away. It entered a five-second confirmation state, then returned the display and fan to their off behavior.

应用在 `UI_OFF`、`UI_BOOT`、`UI_NORMAL` 和 `UI_CONFIRM` 之间切换。关机与启动阶段都把风扇压在 0，启动先显示 Logo，再进入正常采样与控制。关机请求也不是立刻把界面掐掉，而是先进入五秒确认状态，随后让显示和风扇回到关机行为。

This state machine also stopped one input from being interpreted the same way everywhere. A button that woke the unit in `UI_OFF` did not automatically become another event just because the loop saw it again before release. That small latch and release rule is the kind of detail that separates a button read from an interface people can actually use.

状态机还避免了同一个输入在任何时候都被解释成同一件事。`UI_OFF` 里负责唤醒的按键，不会因为手指还没松开、主循环又读到一次，就自动变成下一次操作。这个 latch 与松手规则看着很小，却正好把读到按键和真正能用的交互分开了。

## Bluetooth Stopped Holding the Loop While It Spoke / 蓝牙上报不再占着主循环慢慢说

The first public description reduced Bluetooth to one line, `DATA:<envT>,<outT>,<fan>`. The finished firmware gave that line a clearer execution boundary. `USART1` used `DMA1_Channel4` for asynchronous transmission, so starting a report did not require the application to wait while every byte left the UART. The board sent the compact record every three seconds while active and skipped it in `UI_OFF`.

早期公开描述把蓝牙压成了一条 `DATA:<envT>,<outT>,<fan>`。完成后的固件又给这条报文补上了更清楚的执行边界。`USART1` 通过 `DMA1_Channel4` 异步发送，应用启动一次上报以后，不必站在原地等每个字节离开串口。设备工作时每三秒发送一次，进入 `UI_OFF` 后则停止上报。

The format deliberately stayed small. It did not yet include humidity, protocol versioning, acknowledgement, or a complete fault report. I now read that limitation less as a missing string field and more as a boundary between a bring-up link and a maintainable product protocol. BaseUnit needed the first one to work. It did not pretend the second one was already finished.

报文本身有意保持得很小，没有带湿度、协议版本、应答和完整故障上报。现在再看，我更愿意把这个缺口理解成联调链路与可维护产品协议之间的边界。BaseUnit 先把前一件事做通，没有假装后一件事也已经完成。

## One Fan Setting Turned into a Two-Page Journal / 一个风扇设定值，最后占了两页 Flash

Saving one percentage sounded much easier than designing the failure cases around it. The implementation reserved two Flash pages and wrote records with sequence information, CRC32, and a commit marker. A new setting waited four seconds after the last change before being written. At startup, the firmware scanned for the newest valid record rather than trusting the final bytes it happened to find.

只保存一个百分比，听起来比它周围的故障情况简单多了。实际实现预留了两页 Flash，记录里带序号、CRC32 和 commit 标记。设定变化后先等待四秒，没有新的调整才写入。重新上电时，固件扫描并恢复最后一条有效记录，而不是碰到地址末尾的几个字节就直接相信。

The design accounts for incomplete or corrupted records in its data structure. I do not have a preserved power-cut injection log or an endurance measurement, so I do not turn that structure into a claim that every interrupted write was proven on hardware. What I can say directly is that I implemented the journal, brought the BaseUnit hardware and firmware up, and verified the complete controller on the real machine.

这套数据结构考虑了记录没写完或校验失败的情况，但我没有保留下来的掉电注入日志，也没有擦写寿命实测，所以不会把结构设计直接写成每一种写入中断都已在实机证明。我能直接确认的是，我实现了这套日志，完成了 BaseUnit 的硬件与固件，并在真实机器上把整套控制器跑通。

The BaseUnit did not solve compressor control, EEV timing, or refrigeration safety. It did something that mattered before all three. It proved that I could make sensing, interaction, actuation, communication, and persistence cooperate in one embedded product. After that, opening the ACUnit project no longer felt like starting from zero.

BaseUnit 没有解决压缩机控制、EEV 时序和制冷安全，但它先完成了一件对后三者都很重要的事。传感、交互、执行、通信和持久化真的可以在我写的一套嵌入式产品里协作。做到这里，再打开 ACUnit 工程时，我已经不觉得自己是从零开始了。
