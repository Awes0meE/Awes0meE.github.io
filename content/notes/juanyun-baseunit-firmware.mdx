## Six Responsibilities Share the Loop / 六类职责共用主循环

The existing public note records a compact BaseUnit responsibility set. DHT11 is assigned to ambient temperature and humidity; DHT22 to outlet temperature and humidity. An infrared input represents whether the device is in position, fan PWM carries a 0-100% setting, the OLED shows `ENV / OUT / FAN` plus a shutdown countdown, Bluetooth reports data, and Flash holds settings across a restart.

既有公开笔记记录了一组紧凑的 BaseUnit 职责：DHT11 对应环境温湿度，DHT22 对应出风口温湿度；红外输入表示设备是否在位，风扇 PWM 接收 0-100% 设定，OLED 显示 `ENV / OUT / FAN` 与关机倒计时，蓝牙负责上报，Flash 则跨重启保留设定。

That list reads less like the ACUnit's five-cadence table and more like a state loop. Sensor values enter, presence and key state affect the current mode, a fan command leaves, the screen mirrors selected state, a message summarizes it, and persistent data must be recovered at startup. No periodic intervals are attached to this record, so assigning ACUnit timing values here would only make the two firmware lines look tidier than the material allows.

这份清单不像 ACUnit 的五档周期表，更像一条状态循环：传感值进来，在位与按键状态影响当前模式，风扇命令出去，屏幕映射选中的状态，报文把它压缩后发送，持久化数据还要在启动时恢复。记录没有给这些职责配周期值，硬把 ACUnit 的节拍搬来，只会让两套固件显得比材料本身更整齐。

## Flash Turns One Setting Into a Recovery Problem / Flash 把一个设定值变成恢复问题

The persistence description names a header, records, CRC32, and a commit mark, with the most recent valid setting recovered after restart. Those nouns already reveal the intended failure cases: a record can be incomplete, corrupt, older than another record, or absent. A delayed write is also mentioned in the earlier public description, which would reduce writes when a setting changes repeatedly.

持久化描述里出现了页头、记录、CRC32 与 commit 标记，并写到重启后恢复最近一条有效设定。光是这些名词，就把预期故障摊开了：一条记录可能没写完、校验失败、比另一条更旧，或者根本不存在。此前公开描述还提到延迟写入，用来避免设定值连续变化时反复落 Flash。

There is no linked BaseUnit source, erased-page trace, corruption test, or power-cut recovery log. The record therefore supports the data shape and intended recovery rule, not endurance figures or proof that interrupted writes were handled on a device.

目前没有可链接的 BaseUnit 源码、擦页轨迹、损坏注入测试或掉电恢复日志。因此能保留的是数据形状与预期恢复规则，不能继续推出擦写寿命数字，也不能说设备已经处理过写入中断。

## `DATA:<envT>,<outT>,<fan>` Is the Communication Boundary / 一条 `DATA` 报文划出通信边界

The Bluetooth format is recorded as `DATA:<envT>,<outT>,<fan>`. It packages two temperature fields and one fan field into a short outbound message. The format says nothing about delimiters between frames, numeric precision, humidity fields, acknowledgement, retries, timeout, or what the receiver does with the message.

蓝牙格式记录为 `DATA:<envT>,<outT>,<fan>`，把两路温度字段与一路风扇字段压成一条短报文。单看这个格式，还不知道帧与帧如何分隔、数字精度如何处理、湿度是否另发、有没有应答与重试、超时怎么办，也不知道接收端拿到数据后做什么。

Together, the six responsibilities connect sensing, presence, fan control, display, communication, and persistence as one state problem. Exact timing and on-device behavior remain open until source and logs are available.

这六类职责把传感、在位、风扇控制、显示、通信与持久化连成一个状态问题；精确节拍与目标板行为仍要等源码与日志回答。
